平台主动下发分包数据给设备的协议格式如下：

协议结构：
1. 固定头（Fixed Header）
2. 消息体（Body）
3. 校验尾（CRC + Tail）
-----------------------------------------------------------------------
| 协议字段              | 类型         | 说明                            |
-----------------------------------------------------------------------
| head (1 byte)        | uint8       | 0x5B 包头标识符                  |
-----------------------------------------------------------------------
| version (1 byte)     | uint8       | 协议版本号（默认=1，预留扩展）      |
| length (4 byte)      | uint32      | body长度                        |
| imei (8 byte)        | byte[8]     | 设备IMEI（8位数字字符串）          |
| timestamp (8 byte)   | uint64      | 报文时间戳（毫秒）                |
| seqId (2 byte)       | uint16      | 流水号（递增，溢出后重置）          |
| messageType (1 byte) | uint8       | 消息类型                         |
-----------------------------------------------------------------------
| body (N byte)        | byte[]      | 业务数据体（按 messageType 区分）  |
-----------------------------------------------------------------------
| crc16 (2 byte)       | uint16      | CRC校验                         |
| tail (1 byte)        | uint8       | 0x5D 包尾标识符                  |
-----------------------------------------------------------------------

body结构：
🟢 1️⃣ 升级请求（messageType = 0x81）
    taskId        (8 byte)  long 升级任务ID
    firmwareId    (8 byte)  long 固件ID
    totalPacket   (4 byte)  int 总包数
    chunkSize     (4 byte)  int 分包大小（最后一次分包可能小于分包大小）
    fileSize      (8 byte)  long 文件总大小
    md5           (16 byte) string 文件MD5（二进制）

🟢 2️⃣ 分包数据（messageType = 0x82）🔥核心
    taskId        (8 byte)  long 升级任务ID
    packetNo      (4 byte)
    totalPacket   (4 byte)
    chunkLength   (4 byte)
    chunkData     (N byte)

🟢 3️⃣ ACK确认（messageType = 0x03） 多语义 ACK（Multi-semantic ACK）
    taskId        (8 byte)
    packetNo      (4 byte)
    ackType       (1 byte)

                  ackType 类型说明：
                      ackType =1        UPGRADE_REQUEST_ACK      （上行消息。对应着下行消息类型0x81升级请求的ACK）
                      ackType =2        PACKET_ACK               （上行消息。对应着下行消息类型0x82升级请求的ACK）
                      ackType =4        CANCEL_ACK               （上行消息。对应着下行消息类型0x06升级请求的ACK）
                      ackType =5        HEARTBEAT                 (上行消息。平台无需回复设备的心跳消息)
                  说明：
                      - packetNo 在 ackType=1（升级请求ACK）时可为0
                      - packetNo 在分包ACK时必须对应具体分包序号
                      - PACKET_LAST_ACK 用于通知平台“分包已全部接收完成”，但不代表升级成功

🔴 4️⃣ FAIL失败（messageType = 0x04）
    taskId        (8 byte)
    packetNo      (4 byte)
    errorCode     (2 byte)

🟡 5️⃣ Heartbeat（messageType = 0x05）
    心跳包body无任何内容

🟢 6️⃣ UpgradeResult（messageType = 0x06）🔥最终结果
    imei          (8 byte)  设备imei
    taskId        (8 byte)
    result        (1 byte)  升级结果（0=成功 1=失败）
    errorCode     (2 byte)  失败原因（成功时为0）
    costTime      (4 byte)  升级耗时（秒，可选）

🟠 7️⃣ CancelUpgrade（messageType = 0x87）
    imei          (8 byte)  设备imei
    taskId        (8 byte)
    reason        (1 byte)  取消原因（0=用户取消。目前就只有用户手动点击取消。因为0x07是用户在平台主动点击下发的取消升级指令）



messageType类型描述如下（区分上行 / 下行）：
    - 0x00 ~ 0x7F：设备上行消息（Device → Platform）
    - 0x80 ~ 0xFF：平台下行消息（Platform → Device）

    ---------------- 平台下行（Platform → Device）----------------
    0x81 UpgradeRequest       （开始升级）下行消息：用户平台点击‘开始升级’按钮，主动给设备发升级请求消息
                               平台发送 0x81指令,设备收到该指令，并且对平台做出上行ACK(messageType = 0x03)应答。平台收到ackType =1 后。
                               平台才允许将 upgrade_task.status 从 UPGRADE_REQUESTED 更新为 UPGRADING


    0x82 UpgradePacket         平台开始发送下行消息 0x82 UpgradePacket 分包数据。

    0x87 CancelUpgrade         （取消升级🔥）用户平台人工主动点击“取消升级”按钮，下发取消升级指令


    ---------------- 设备上行（Device → Platform）----------------
    0x10 DeviceBootUpMessage   （设备上线）NettyClient连接上 NettyServer 后发送上线通知包（只在连接上线发送一次）

    0x03 ACK                   （确认响应）设备对平台指令或分包的确认（通过 ackType 区分语义）

    0x04 FAIL                  （分包失败）设备回复升级失败。比如说：在upgrading过程中，设备此时接受到的分包(chunkData)crc16计算结果与本次body封装的crc16结果不一致

    0x05 Heartbeat             （心跳）设备定时上报，维持在线状态，防止被 IdleStateHandler 误踢下线

    0x06 UpgradeResult         （最终结果🔥）设备完成升级后上报结果（成功 / 失败）
-----------------------------------------------------------------


-----------------protocol description end------------------------------------


设备升级整个过程中，关于设备升级状态(upgrade_task表的status字段）状态流转过程如下：
    目前设备升级状态分为以下类型：
    IDLE（设备未绑定固件）设备未绑定固件，平台首次添加的该设备。status=FIREWARE_BIND
    ↓
    FIREWARE_BIND（已绑定固件）用户在平台操作，选择该设备绑定固件。 status=FIREWARE_BIND
    ↓
    UPGRADE_REQUESTED（已下发升级指令）平台已下发0x81升级指令，并且等待该指令的ACK。此时更新 status=UPGRADE_REQUESTED
    ↓
    UPGRADE_READY（升级就绪）设备收到0x81消息【此时设备将收到的0x81 body结构里面有关固件分包信息给保存下来，方便后续收到平台下发的所有分包后，设备端将所有分包按PacketNo升序排序后，合并成一个文件，然后与0x81消息体里面的md5值做比较，相同则表示固件无误。
                            可以考虑给fota-mock-device-client 模拟工程单独分配一个数据库环境。创建2张设备表。设备表(devive)，该表有如下字段：主键id、设备imei、设备固件当前版本号、固件md5值、总分包数totalPacket、文件大小fileSize、create_at；固件分包表(fireware_packet)，该有:主键id、设备imei、task_id、分包数据packet_data,created_at】，
                           并且给平台ACK响应。此时更新 status=UPGRADE_READY
    ↓
    UPGRADING（升级中） 平台开始下发固件分包消息（messageType=0x82），设备收到该类型的消息后，给平台回复上行消息（messageType=0x82）。此时更新 status=UPGRADING。这个过程往返多次，持续时间一般是在30s至1分钟左右
                       🔥设备收到完整的分包（设备收到0x82的个数等于协议包totalPacket的个数）。并且对总包数按照packetNo升序排序，
                       然后合并文件、计算md5值（与之前收到的0x01消息体body里面的md5值做比较，若对比的md5值相同，则发送上行消息(0x06)成功,否则就发送上行消息(0x06)失败）
                       平台收到设备0x06类型上行消息，就将升级中状态更新为升级成功或升级失败(取决于md5比较结果)。
    ↓
    SUCCESS（成功） 设备上报 0x06类型的消息，result=0表示成功
    ↓
    FAIL（失败）  设备上报 0x06类型的消息，result=1表示失败
    ↓
    TIMEOUT（超时）平台在150秒内，若无法收到设备上行ACK消息【必须是业务类型的ACK。0x05 Heartbeat 不算在内】

    PAUSED（升级暂停） 如果设备突然掉线 就更新为PAUSED，升级暂停状态只会出现在upgrading过程中 设备断线的时候，才会产生这个状态。

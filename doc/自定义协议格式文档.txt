平台主动下发分包数据给设备的TCP协议格式如下：

协议结构：
1. 固定头（Fixed Header）
2. 消息体（Body）
3. 校验尾（CRC + Tail）
-----------------------------------------------------------------------
| 协议字段              | 类型         | 说明                            |
-----------------------------------------------------------------------
| head (1 byte)        | uint8       | 0x5B 包头标识符                  |
-----------------------------------------------------------------------
| version (1 byte)     | uint8       | 协议版本号（默认=1，预留扩展）      |
| length (4 byte)      | uint32      | body长度                        |
| imei (8 byte)        | byte[8]     | 设备IMEI（8位数字字符串）          |
| timestamp (8 byte)   | uint64      | 报文时间戳（毫秒）                |
| seqId (2 byte)       | uint16      | 流水号（递增，溢出后重置）          |
| messageType (1 byte) | uint8       | 消息类型                         |
-----------------------------------------------------------------------
| body (N byte)        | byte[]      | 业务数据体（按 messageType 区分）  |
-----------------------------------------------------------------------
| crc16 (2 byte)       | uint16      | CRC校验                         |
| tail (1 byte)        | uint8       | 0x5D 包尾标识符                  |
-----------------------------------------------------------------------

body结构：
------------下行消息的body结构--------------------------
🟢 1️⃣ 升级请求（messageType = 0x81）
    taskId        (8 byte)  long 升级任务ID
    firmwareId    (8 byte)  long 固件ID
    firmwareNameLen (1 byte) byte 固件包名称长度
    firmwareName  (N byte)  byte[] 固件包名称
    firmwareVersionLen (1 byte)  byte 固件包版本号长度
    firmwareVersionName (N byte) byte[] 固件包版本名称
    totalPacket   (4 byte)  int 总包数
    chunkSize     (4 byte)  int 分包大小（最后一次分包可能小于分包大小）
    fileSize      (8 byte)  long 文件总大小
    md5           (16 byte) string 文件MD5（二进制）

🟢 2️⃣ 分包数据（messageType = 0x82）🔥核心
    taskId        (8 byte)  long 升级任务ID
    packetNo      (4 byte)  int 分包序号
    totalPacket   (4 byte)  int 总包数
    chunkLength   (4 byte)  int 固件包分片的长度
    chunkData     (N byte)  byte[] 固件包分片数据

🟢 3️⃣平台ACK确认（messageType = 0x83）网关收到设备上行消息，对设备做出通用应答
    taskId         (8 byte)  long  关联任务ID，🔥注意：非升级场景可为0。例如给0x10做应答，则taskId为 0
    refMessageType (1 byte)  uint8 被确认的原始上行消息类型
    ackStatus      (1 byte)  uint8 确认结果（0=成功收到 1=拒绝/失败）
    reasonCode     (1 byte)  uint8 原因码（成功时为0，失败时可扩展）
        🔥refMessageType 类型说明：
            表明这条 0x83 是在确认哪一种设备上行消息。
            例如：
                •   0x10：表示确认 DeviceBootUp。
                •   0x06：表示确认 UpgradeResult
            这是 0x83 body 里最关键的字段。

        ackStatus 类型说明：
            0 = ACK_OK        平台已成功接收并处理
            1 = ACK_REJECT    平台拒绝/处理失败
            当前阶段甚至几乎只会用到 0。 但保留 1 很有扩展性。

        🔥reasonCode 类型说明：
            0 = NONE
            1 = UNKNOWN_MESSAGE
            2 = TASK_NOT_FOUND
            3 = DUPLICATE_RESULT
            4 = INVALID_STATE
            成功就填 0，失败暂时统一填 1


🟠 4️⃣CancelUpgrade（messageType = 0x87）
    taskId        (8 byte)  任务Id
    reason        (1 byte)  取消原因（0=用户取消。目前就只有用户手动点击取消。因为0x07是用户在平台主动点击下发的取消升级指令）




🟢 5️⃣DeviceBootUp（messageType = 0x10）
    currentFirmwareVersionLength  (1 byte)  当前固件版本号长度
    currentFirmwareVersion        (N byte)  当前固件版本号，UTF-8字符串，例如 v1.0.0
    deviceTypeLen				  (1 byte)  设备类型长度
    deviceType					  (N byte)  设备类型
        🔥说明：
        - 设备建立连接后发送，仅发送一次
        - 平台收到后更新设备在线状态
        - 平台收到后可回填 device.current_firmware_version



🟢 5️⃣设备ACK确认（messageType = 0x03） 针对平台下发指令的多语义 设备ACK（Multi-semantic ACK）。
    taskId        (8 byte) 任务Id
    packetNo      (4 byte) 分包序号
    ackType       (1 byte) 应答类型
        ackType 类型说明：
        ackType =1        UPGRADE_REQUEST_ACK      （上行消息。对应着下行0x81消息类型的ACK）
        ackType =2        PACKET_ACK               （上行消息。对应着下行0x82消息类型的ACK）
        ackType =4        CANCEL_ACK               （上行消息。对应着下行0x87消息类型的ACK）
        ackType =5        HEARTBEAT                 (上行消息。平台无需回复设备的心跳消息)
        ackType =6        BUSY                      (上行消息。mock-device服务的业务线程写本地固件文件触发背压消息，服务端收到该消息后 降低packetSend的速率)
            说明：
            - packetNo 在 ackType=1（升级请求ACK）时可为0
            - packetNo 在分包ACK时必须对应具体分包序号
            - PACKET_LAST_ACK 用于通知平台“分包已全部接收完成”，但不代表升级成功

🔴 6️⃣FAIL失败（messageType = 0x04）
    taskId        (8 byte)
    packetNo      (4 byte)
    errorCode     (1 byte) 1以上的值（包含1）都是网关层面的网络，掉线，等失败原因。参考类定义：/Users/fengye/IdeaProjects/fota-project/fota-gateway-tcp-server/src/main/java/com/yef/protocol/UpgradeFailErrorCode.java

🟡 7⃣ Heartbeat（messageType = 0x05）
    心跳包body无任何内容

🟢 8⃣ UpgradeResult（messageType = 0x06）🔥最终结果
    taskId        (8 byte)
    result        (1 byte)  升级结果（0=成功 1=失败）
    errorCode     (1 byte)  失败原因（成功时为0）
    costTime      (4 byte)  升级耗时（秒，可选）




messageType 类型文档定义：
基础规则
---------------------------------------------------------------------------
| 数值范围        | 方向                     | 说明                     |
---------------------------------------------------------------------------
| 0x00 ~ 0x7F     | Device → Platform       | 设备上行消息             |
| 0x80 ~ 0xFF     | Platform → Device       | 平台下行消息             |
---------------------------------------------------------------------------

--------------------------- 平台下行（Platform → Device） --------------------
---------------------------------------------------------------------------
| messageType | 名称              | 说明                                     |
---------------------------------------------------------------------------
|             |                   | 开始升级指令                              |
|             |                   | 平台触发升级流程，下发固件元信息             |
| 0x81        |  UpgradeRequest   | 设备收到后需返回 ACK(ackType=1)            |
|             |                   | 平台收到 ACK 后，状态进入 UPGRADING         |
---------------------------------------------------------------------------
|             |                   | 固件分包数据                              |
| 0x82        | UpgradePacket     | 平台按顺序发送分包（packetNo递增）           |
|             |                   | 设备逐包返回 ACK(ackType=2)               |
---------------------------------------------------------------------------
|             |                   | 通用应答【平台回复设备】                    |
|             |                   | 平台对设备关键上行通知消息的确认响应。        |
| 0x83        | Platform ACK      | 当前主要用于确认：                         |
|             |                   |   1. DeviceBootUp（0x10）                |
|             |                   |   2. UpgradeResult（0x06）               |
---------------------------------------------------------------------------
|             |                   | 取消升级指令                              |
| 0x87        | CancelUpgrade     | 用户手动触发取消升级                        |
|             |                   | 设备收到后应停止升级并返回 ACK(ackType=4)    |
---------------------------------------------------------------------------


--------------------------- 设备上行（Device → Platform） --------------------
---------------------------------------------------------------------------
| messageType | 名称              | 说明                                    |
---------------------------------------------------------------------------
| 0x10        | DeviceBootUp      | 设备上线通知                             |
|             |                   | 建立连接后发送，仅发送一次                  |
---------------------------------------------------------------------------
| 0x03        | Device ACK        | 通用应答【设备回复平台】                    |
|             |                   | 通过 ackType 区分具体语义                  |
|             |                   | 用于 UpgradeRequest / UpgradePacket 等确认|
---------------------------------------------------------------------------
| 0x04        | FAIL              | 分包失败                                  |
|             |                   | 分包校验失败（如 CRC 校验不通过）            |
-----------------------------------------------------------------------------｜
| 0x05        | Heartbeat         | 心跳包                                    |
|             |                   | 定时上报，维持连接                          |
|             |                   | 平台无需回复                               |
---------------------------------------------------------------------------
| 0x06        | UpgradeResult     | 升级最终结果                               |
|             |                   | 升级完成后上报（成功 / 失败）                |
---------------------------------------------------------------------------
备注：所有的上行消息，平台只需要对0x10和0x06指令类型的消息做出应答即可，其它消息【0x03、0x04、0x05】 网关不做应答。










设备升级整个过程中，关于设备升级状态(upgrade_task表的status字段）状态流转过程如下：
    目前设备升级状态分为以下类型：
    IDLE（设备未绑定固件）设备未绑定固件，平台首次添加的该设备。status=FIREWARE_BIND
    ↓
    FIREWARE_BIND（已绑定固件）用户在平台操作，选择该设备绑定固件。 status=FIREWARE_BIND
    ↓
    UPGRADE_REQUESTED（已下发升级指令）平台已下发0x81升级指令，并且等待该指令的ACK。此时更新 status=UPGRADE_REQUESTED
    ↓
    UPGRADE_READY（升级就绪）设备收到0x81消息【此时设备将收到的0x81 body结构里面有关固件分包信息给保存下来，方便后续收到平台下发的所有分包后，设备端将所有分包按PacketNo升序排序后，合并成一个文件，然后与0x81消息体里面的md5值做比较，相同则表示固件无误。
                            可以考虑给fota-mock-device-client 模拟工程单独分配一个数据库环境。创建2张设备表。设备表(devive)，该表有如下字段：主键id、设备imei、设备固件当前版本号、固件md5值、总分包数totalPacket、文件大小fileSize、create_at；固件分包表(fireware_packet)，该有:主键id、设备imei、task_id、分包数据packet_data,created_at】，
                           并且给平台ACK响应。此时更新 status=UPGRADE_READY
    ↓
    UPGRADING（升级中） 平台开始下发固件分包消息（messageType=0x82），设备收到该类型的消息后，给平台回复上行消息（messageType=0x82）。此时更新 status=UPGRADING。这个过程往返多次，持续时间一般是在30s至1分钟左右
                       🔥设备收到完整的分包（设备收到0x82的个数等于协议包totalPacket的个数）。并且对总包数按照packetNo升序排序，
                       然后合并文件、计算md5值（与之前收到的0x01消息体body里面的md5值做比较，若对比的md5值相同，则发送上行消息(0x06)成功,否则就发送上行消息(0x06)失败）
                       平台收到设备0x06类型上行消息，就将升级中状态更新为升级成功或升级失败(取决于md5比较结果)。
    ↓
    SUCCESS（成功） 设备上报 0x06类型的消息，result=0表示成功
    ↓
    FAIL（失败）  设备上报 0x06类型的消息，result=1表示失败
    ↓
    TIMEOUT（超时）平台在150秒内，若无法收到设备上行ACK消息【必须是业务类型的ACK。0x05 Heartbeat 不算在内】

    PAUSED（升级暂停） 如果设备突然掉线 就更新为PAUSED，升级暂停状态只会出现在upgrading过程中 设备断线的时候，才会产生这个状态。

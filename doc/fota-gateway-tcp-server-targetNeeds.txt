一、先定网关职责
fota-gateway-tcp-server 本质上做四件事：
	1.	管理连接
	2.	解析协议
	3.	维护设备会话
	4.	驱动升级流程
所以它不是简单的 TCP server，而是一个 连接管理 + 协议网关 + 升级执行节点。




二、服务端 pipeline 推荐结构
现在 childHandler(null) 这里是不合理的，你定义这样的一条链：
    IdleStateHandler
    → FotaFrameDecoder
    → FotaMessageDecoder
    → DeviceIdentityHandler
    → UpgradeDispatchHandler
    → FotaMessageEncoder
    → ExceptionHandler




三、定义 Handler 职责划分
1. IdleStateHandler
作用是连接保活和断线检测。
服务端建议：new IdleStateHandler(90, 0, 0)
意思是 90 秒没收到设备数据，就认为设备离线。
职责只有两个：
第一，触发 userEventTriggered。
第二，交给后面的业务 handler 去做离线处理。
它不负责业务状态更新，不负责删 session，不负责改升级状态。

2. FotaFrameDecoder
这是 半包/粘包处理器。
目前的协议固定为：head(1) + version(1) + length(4) + messageType(1) + body(N) + crc16(2) + tail(1)
你也可以参考协议格式文档，文档所在位置：/Users/fengye/IdeaProjects/fota-project/doc/protocol-format.txt
所以这个 decoder 负责：
	•	校验包头包尾是否正确
	•	根据 length 提取完整帧
	•	丢掉非法帧
	•	不做业务解析
它的输出最好是一个原始帧对象，比如：
class FotaPacketFrame {
    byte version;
    byte messageType;
    byte[] body;
    int crc16;
}
这样下一层只关心“完整消息”，不关心 ByteBuf。



3. FotaMessageDecoder
这一层才是 协议消息反序列化。根据 messageType 把 body 解析成不同 POJO。
建议你先定义四类消息：
    0x01 UpgradeRequestMessage   平台→设备
    0x02 UpgradePacketMessage    平台→设备
    0x03 AckMessage              设备→平台
    0x04 FailMessage             设备→平台

messageType类型：
    0x01 = 升级请求（平台 → 设备）
    0x02 = 分包数据（平台 → 设备）
    0x03 = ACK确认（设备 → 平台）
    0x04 = FAIL失败（设备 → 平台）

虽然服务端大多数时候收的是 0x03 和 0x04，但服务端和客户端最好共用同一套协议对象，后面 mock-device 也能直接复用。
这一层职责：
	•	校验 CRC16
	•	解析 body
	•	输出业务消息对象
这一层不要碰 Redis，不要碰 DB，不要改升级状态。



4. DeviceIdentityHandler
这是很关键的一层。
它负责把“连接”和“设备”绑定起来。我已经确定了 协议里设备侧认的是 imei，系统内部认的是 device_id。
所以这里职责是：
	•	从上行消息里拿到 imei
	•	查 Redis 或缓存映射 imei -> deviceId
	•	把 imei / deviceId / taskId 放到 Channel Attribute 里
	•	首次识别设备时，注册 session 到 SessionManager
比如：
    Channel.attr(IMEI)
    Channel.attr(DEVICE_ID)
    Channel.attr(CURRENT_TASK_ID)
这一层相当于把“原始消息”提升成“已识别设备消息”。如果当前连接还没识别出设备身份，就不能进入升级调度层。

5. UpgradeDispatchHandler
这一层才是网关的业务核心。
它负责处理：
	•	设备 ACK
	•	设备 FAIL
	•	设备上线后的恢复逻辑
	•	设备断线后的暂停逻辑
	•	推进升级状态机
它不做协议解析，不做 ByteBuf 操作，只处理已经解好的业务消息对象。
你后续会在这里根据 messageType 分发：收到 ACK，如果是“升级请求 ACK”，就把任务状态从：
UPGRADE_REQUESTED -> UPGRADING
然后启动分包发送。
如果是“分包 ACK”，就更新当前包进度，继续发下一包。
收到 FAIL
记录 device_upgrade_log，更新任务失败原因，必要时重试或失败终止。
设备重连
如果发现当前设备有 PAUSED 状态的任务，就尝试恢复锁并继续传输。

6. FotaMessageEncoder
这是出站 handler。
负责把服务端要下发的：
	•	UpgradeRequestMessage
	•	UpgradePacketMessage
编码成你的协议格式。
职责：
	•	组装 body
	•	计算 bodyLength
	•	计算 CRC16
	•	写 head/tail
它不做状态推进，不决定发什么，只负责“怎么编码”。

7. ExceptionHandler
最后一层统一兜底。
职责：
	•	打日志
	•	关闭非法连接
	•	通知 SessionManager 清理会话
	•	必要时把升级状态改成 PAUSED 或 FAIL




四、我建议你应该这样去理解服务端入站和出站
入站 Inbound
设备发消息给平台：
    设备ACK / FAIL / 上线消息
    → FrameDecoder
    → MessageDecoder
    → DeviceIdentityHandler
    → UpgradeDispatchHandler
出站 Outbound
平台发消息给设备：
    UpgradeService / PacketSender
    → writeAndFlush(message)
    → MessageEncoder
    → Socket
所以出站不是在 handler 里“主动发”，而是业务层拿到 channel 之后：
channel.writeAndFlush(upgradePacketMessage);
然后交给 Encoder。




五、我这个 FOTA升级 场景里，最少需要的消息类型
我建议现在最小闭环只做这 4 种：
1. 设备上线注册消息
虽然你不做 0x05 心跳，但我建议你至少保留一个“首次注册/上线消息”。
比如：
    0x10 DeviceRegisterMessage
body:
    imei
    firmwareVersion
    deviceType
作用：
	•	建立 session
	•	映射 channel 和设备
	•	平台显示设备在线
	•	上报当前版本
这个消息非常重要，否则服务端怎么知道“这个连接是谁”。

2. 0x01 升级请求
平台告诉设备：
    你准备开始升级
    这是 taskId
    这是 firmwareId
    这是总包数
    这是 chunkSize
    这是 md5
设备收到后回复 ACK。

3. 0x02 分包数据
平台开始一包一包下发。

4. 0x03 ACK / 0x04 FAIL
设备对每次请求和每个分包做回应。




六、服务端状态流转，和 handler 的对应关系
这里涉及到设备升级到升级完成的整个状态类型（status）的流转，目前我设计的状态流程分为如下几个状态：
    IDLE（空闲/可升级）
    ↓
    READY（已绑定固件）
    ↓
    UPGRADE_REQUESTED（已下发升级指令，等待ACK）
    ↓
    UPGRADING（升级中）
    ↓
    SUCCESS（成功）
    ↓
    FAIL（失败）
    ↓
    TIMEOUT（超时）
    还有一个，PAUSED 状态（升级暂停，注意：只有是处于UPGRADING状态的升级状态，且设备掉线，才能更新为此状态）。
    如果设备突然掉线 就更新为此状态（upgrade_task表的status字段分别有这些个升级状态类型）后续设备断线重新连接，就可以做断点续传。从上一次分包的packetNo接着开始

我建议 handler 和设备升级状态（status）按照如下关系对应起来。
1. 用户点击“开始升级”
这是 web 服务干的事，不在 Netty handler 内。
状态：
    READY -> UPGRADE_REQUESTED
并抢 Redis 锁（lua脚本）。由于我一个设备可以被多个用户所看见【我的fota web管理平台多个用户可以看到同一个设备】，
所以防止多个用户操作同一台设备，必须做CAS抢占设备，只有一个CAS线程才能抢占设备升级任务成功，其它线程均失败。
由于我这个fota都部署在K8S集群上，并且每个服务都是3个实例。所以用户点击“开始升级”要做分布式全局唯一性，我打算用redis+lua脚本做分布式锁，且锁的默认超时释放时间是30s,
但要考虑锁续期的问题，因为整个fota下载固件的过程大概是在30s至1分钟的时间范围。并且如果在升级过程中，设备如果掉线了，应该要释放锁。
当设备重新连接后，应该重新获取锁。
锁的设计方式是：短TTL + 定时续约 + 业务判断

    ✔ 当前 upgradeId 匹配

2. 网关下发 0x01 升级请求
由业务服务拿到 session 后发出，不是 handler 自己乱发。

3. 设备 ACK 升级请求
进入服务端 inbound：
    FotaFrameDecoder
    → FotaMessageDecoder
    → DeviceIdentityHandler
    → UpgradeDispatchHandler
然后升级状态状态：
    UPGRADE_REQUESTED -> UPGRADING

4. 开始分包发送
由 PacketSender / UpgradeExecutor 做，不要塞到 handler 里。

5. 收到每包 ACK
UpgradeDispatchHandler 更新进度：currentPacket + 1

6. 设备断线
在 userEventTriggered 或 channelInactive 中：UPGRADING -> PAUSED
停止续约锁，等待恢复。

------------------------以下是fota-mock-device-client职责描述-------------------------
十一、fota-mock-device-client这个module（nettyClient客户端）的总职责如下：
1. 建立连接并注册设备身份
2. 接收并解析平台下发的协议消息
3. 校验每一个分包的正确性（CRC16）
4. 管理分包接收进度和缓存
5. 在全部分包接收完成后合并固件
6. 对整包做 MD5 校验
7. 根据结果回复 ACK / FAIL，并支持掉线恢复
如果你想更像真实设备，还可以继续补两类：
8. 模拟 Flash 写入过程
9. 模拟异常行为（丢包、CRC失败、写入失败、重连）




十二、设备客户端的生命周期
关于这个 nettyClient 的生命周期，我建议定义成这样：
启动
→ 连接 gateway
→ 发送 DeviceRegisterMessage
→ 等待升级请求
→ 收到升级请求并 ACK
→ 接收分包
→ 每包 CRC16 校验
→ 写入本地缓存/文件
→ 全部接收完成
→ 合并固件
→ 整包 MD5 校验
→ 成功则 ACK 最终成功
→ 失败则 FAIL
这个流程和真实设备非常像。




十三、设备上线时它要做什么
客户端启动后，不是单纯 connect 完就结束了，而是要主动告诉平台：“我是谁，我现在在线，我当前是什么版本”
所以连接成功后，它应该立即发一个注册消息。建议你这个 DeviceRegisterMessage 至少带：
imei
firmwareVersion
deviceType

这个动作有四个作用：
第一，平台能识别当前连接属于哪个设备。
第二，平台能把这个设备标记为在线。
第三，平台能知道设备当前固件版本。
第四，如果这个设备之前有 PAUSED 的升级任务，平台可以决定是否恢复。
所以，nettyClient 的第一个核心职责不是“等平台发命令”，而是：主动注册身份

十四、收到升级请求后，它要做什么
平台先发的是 0x01 升级请求，这个消息不是分包本体，而是“升级会话初始化消息”。
设备收到后，不应该立刻认为升级开始了，而是要先做一轮“前置校验”。
建议做这些检查：
1. 检查当前是否已有升级任务
如果当前设备还在执行旧任务，或者本地还有未完成上下文，要决定是否接受新任务。
2. 检查 taskId 是否重复
如果同一个 taskId 已经初始化过，就要做幂等处理，不能重复创建上下文。
3. 初始化升级上下文
比如建立一个本地对象：
taskId
firmwareId
totalPacket
chunkSize
fileSize
md5
receivedPacketSet
tempFilePath
status

4. 创建临时固件接收文件
不能等所有分包都进内存再拼，因为真实设备内存很小。
即便 mock client 在 PC 上跑，我也建议你模拟真实行为：边接收边写临时文件。

5. 回复 ACK
如果前置检查通过，再回平台 ACK，表示：“这个任务我接受了，可以开始发包”
这里的 ACK 很重要，它不是“某个分包收到了”，而是“升级会话初始化成功”。

十五、为什么每一包都要做 CRC16 校验？
这是我特意提到的重点，我详细讲。先给一句核心定义：
    CRC16 是“分包级实时校验”
    MD5 是“整包级最终校验”
它们解决的不是同一个问题。

1. 为什么不能只靠整包 MD5
假设你只做整包 MD5，不做分包 CRC16，会发生什么？
    平台发了 200 个包
    第 137 包在传输过程中坏了
    设备完全不知道
    继续把后续包全收完
    最后整包 MD5 比对失败
结果就是：
    前面所有传输都白费了
    只能整包重来
这在 LoRa、弱网、串口、蓝牙这类链路上代价极高。
所以必须在每一包到达时就立刻判断：如果这一包不对，只重传这一包，而不是整包重来。

2. CRC16 为什么适合“每一包”？因为它有这几个特点：
速度快，设备 MCU 算得动，成本低。
足够轻，2 个字节就够了，不会让包体膨胀太大。
适合实时传输，收到一包立刻算一次，不需要等整文件结束。
所以设备端针对每一包都应该：
取出 payload，自己计算 CRC16，和包里的 crc16 比较，立刻 FAIL，要求平台重传该 packetNo。
这就是分包 CRC16 的真正意义：把错误控制在“单包级别”

十六、收到每一个分包后，设备端具体要做什么
这个流程建议你严格做成固定步骤。

Step 1：检查任务上下文是否存在
如果这个 taskId 没有初始化上下文，说明包非法，直接丢弃或 FAIL。

Step 2：检查 packetNo 是否合法
比如：
	•	小于 1
	•	大于 totalPacket
	•	已经收过
都属于异常或重复包。

Step 3：做 CRC16 校验
这是必须步骤。
如果失败：回复 FAIL(taskId, packetNo, CRC_ERROR)

Step 4：校验通过后写入缓存/文件
这里建议不要只存在内存里，建议写入本地临时文件或者随机访问文件。因为真实设备逻辑更接近：收到一包 → 校验 → 落盘/写Flash缓冲

Step 5：更新接收进度
比如：
    receivedPacketCount++
    maxReceivedPacketNo
    bitmap / Set<packetNo>

Step 6：回复 ACK
告诉平台：
    taskId
    packetNo
    status=ACK
这样平台才会继续发下一包。




十七、为什么“收到所有分包后还要做整包 MD5”
因为：每一包都对 ≠ 整个文件一定对
举个例子：
	•	包顺序写错了
	•	某个包重复写了两次
	•	中间偏移写错
	•	合并逻辑出 bug
这些情况，每个分包的 CRC16 都可能通过，但最终拼出来的文件仍然是坏的。
所以在所有分包完成后，设备端必须做最终校验：对临时固件文件计算 MD5 与升级请求里的 md5 比较。
如果一致：说明整包真正可用。设计就可以将这次下载下来的固件包进行本次版本升级的固件包
如果不一致：说明最终固件不完整或拼接错误。这时要回复 FAIL，设备不能使用这次下载的固件包进行本次升级操作。




十八、收到所有分包后，设备端的完整职责
这个阶段不是“收完就结束”，而是还要做后处理。
1. 检查是否所有 packetNo 都收齐，不能只看收到数量，还要看序号是否连续。
2. 合并临时文件
如果你是边写同一个临时文件，这一步可以省略；
如果你是每包一个小文件，那这里要合并。
你看你打算怎么做吧。
3. 校验整包 MD5
这是必须做的最终一致性校验。

4. 模拟写入固件区 / Flash
即使我现在只是 mock，也建议你留出一个步骤来模拟：
接收成功 ≠ 升级完成
真实世界里还有一个：把新固件刷入设备存储

这个动作可能失败，比如：
	•	Flash 写失败
	•	空间不足
	•	擦写异常

所以 mock client 最好也模拟一个“安装阶段”。

5. 更新本地版本号
如果升级成功，设备下次注册时应上报新版本号。

6. 回复最终结果
可以设计成最后一个 ACK，或者一个单独的成功消息。

十九、nettyClient 除了收包校验，还要做哪些暂时没考虑到的事？下面这些点建议补上。
1. 幂等处理
如果平台因为网络问题重复下发同一个包，设备不能重复写坏。
所以要支持：
同一个 taskId + packetNo 重复到达
设备应判断：
	•	如果已经成功处理过，可以直接 ACK
	•	不要重复写入
这就是幂等性。


2. 乱序处理
当前如果平台是“收到 ACK 再发下一包”，理论上不会乱序。
但后面如果你想做滑动窗口并发发送，就会出现乱序。
所以设备端最好具备一个基础能力：
packetNo 不一定严格顺序到达
即便现在先不实现滑动窗口，结构上也要留这个余地。

3. 断点续传上下文保存
如果设备升级到一半断线了，下次重连后要能继续。
所以 nettyClient 本地要保存：
    taskId
    currentReceivedPacketNo / bitmap
    临时文件路径
    md5
    chunkSize
    totalPacket

不能只放内存里，否则进程一重启就全丢了。
你可以先做简化版：
	•	内存保存
	•	掉线不断进程时恢复
后面再升级为文件持久化。

4. 失败原因分类
因为平台侧失败统一是 FAIL，所以失败原因的细节则需要去看日志。
设备侧也应该有明确错误分类，至少建议这些：
    CRC_ERROR
    TASK_NOT_FOUND
    PACKET_DUPLICATE
    PACKET_OUT_OF_RANGE
    MD5_MISMATCH
    FLASH_WRITE_ERROR
    INTERNAL_ERROR
这样 mock client 返回 FAIL 时，平台才能写出真正有价值的 device_upgrade_log。

5. 本地资源清理
升级成功或失败后，临时文件、上下文、缓存都要清理。
否则会出现：
	•	磁盘堆积
	•	老任务干扰新任务
	•	重连后误恢复旧任务

6. 重连机制
mock client 最好支持自动重连，模拟真实设备行为。
断线后：
	等待 3 秒
    重新 connect
    重新注册 DeviceRegisterMessage
    尝试恢复任务
这对于验证 PAUSED -> UPGRADING 的恢复链路非常重要。


7. 升级期间禁止接受新任务
你前面在平台侧做了锁控制，但设备侧也建议防御一层。
如果设备当前 taskId=A 还没结束，又收到 taskId=B 的升级请求，设备应明确拒绝，避免本地状态混乱。
这叫：
    设备侧自我保护

8. 模拟真实设备写入耗时
如果 mock client 收到分包就立刻 ACK，整个链路会太理想化。
建议适当模拟：
	•	每包写入耗时 20~100ms
	•	偶发失败
	•	偶发断线

这样 gateway 和状态机才经得住测试。




二十、 nettyClient 的职责可以总结成一句话
它不是“被动收消息的客户端”，
而是“设备升级过程的执行者和校验者”。




二一、我给出一版适合写进设计文档的职责说明
fota-mock-device-client 职责：
1. 启动后主动连接网关，并发送设备注册消息，建立设备身份与连接的绑定关系
2. 接收平台下发的升级请求消息，初始化本地升级上下文，并回复 ACK
3. 接收固件分包，对每一包执行 CRC16 校验，保证传输过程中的单包正确性
4. 将校验通过的分包写入本地临时缓存或临时文件，维护接收进度和 packetNo 状态
5. 对重复包、非法包、越界包进行幂等和防御处理
6. 在全部分包接收完成后，合并生成完整固件文件，并对整包执行 MD5 校验，保证最终文件完整性
7. 在整包校验成功后，模拟设备写入固件区或刷写 Flash 的过程，并更新本地固件版本
8. 在升级失败时返回 FAIL，并携带明确错误原因；在升级成功时返回最终成功确认
9. 在连接断开时支持自动重连，并在重连后基于 taskId 和本地进度尝试断点续传
10. 通过模拟延迟、丢包、CRC 失败、写入失败等异常行为，帮助验证网关和升级状态机的健壮性
